## 1. Verified strengths

1. **Layering is real, not cosmetic.** Every runtime follows `domain/` (frozen dataclasses,
   validation in `__post_init__`), `application/` (managers), `infrastructure/` (SDK
   adapters). SDK types never leak past `gemini_provider.py` / `openai_provider.py`.
2. **Capability boundary is defense-in-depth.** The LLM sees only allowlisted tool
   definitions (`_tool_definitions`), *and* every returned call is re-validated
   (existence → permission → schema) in `ToolSafetyGate`. Rejections return generic
   LLM-safe strings and emit `tool.rejected`.
3. **Correlation works end to end.** Observed live: `agent.status_changed → agent.started →
   llm.requested → llm.failed → agent.status_changed`, all carrying the same
   `interaction_id`.
4. **Reusable-agent correction holds for normal failures.** An LLM failure mid-interaction
   returns the Agent to IDLE (`except Exception: finish_interaction`). Concurrent chats are
   serialized by `AgentManager._lock` + the `RUNNING → RUNNING` guard.
5. **Secret hygiene in the Gemini adapter.** `_sanitized_error_message` redacts the key,
   request content, and `api_key=`-style fragments before logging.
6. **Bounded in-memory stores everywhere** (event history, tool task history, memory
   provider capacity, workflow history) — no unbounded growth except sessions (H6).
7. **Fast, deterministic test suite** (131 tests in < 1 s) with provider fakes.
8. **Frontend transport layer is typed and centralized** (`requestJson`, per-domain
   services, backend `detail` surfaced as error messages).

## 2. Critical bugs / blockers

### C1 — Manual lifecycle controls can permanently brick a reusable Agent · CONFIRMED

**Evidence (live):** `initialize → POST /start` ⇒ status `running` with no interaction.
Every chat then fails `409 "cannot transition from 'running' to 'running'"`.
`pause → resume` returns to `running`. The only exit is `stop`, and `STOPPED` is terminal
(`initialize` after stop → 409).

**Why it happens:** since v0.10D, `RUNNING` means "an interaction is in progress" and is
owned by `AgentInteractionService`. But `POST /start|/pause|/resume` (and
`agent-card.tsx:42-50`) still treat it as a user-controlled process state. In the UI,
**the primary buttons on an IDLE Agent are "Start" and "Stop"** — the natural first click
breaks the Agent.

A second path: `POST /pause` during an in-flight chat → `finish_interaction` attempts
`PAUSED → IDLE`, which is not an allowed transition → `AgentLifecycleError` (raised twice:
once from the success path, once from the `except` handler) → chat returns 409 and the Agent
is stuck PAUSED → RUNNING.

**Impact:** any website user can make an Agent unusable in one click; data/session lost
because the only recovery is delete + recreate.

**Fix:** (a) Remove Start/Pause/Resume from the UI. (b) Backend: `start/pause/resume` endpoints
return 409 "Agent activity is managed by interactions" (or are removed from the router —
decision needed, see §8). (c) Make `finish_interaction` tolerant: if the Agent is no longer
RUNNING (e.g. STOPPED mid-chat), leave it unchanged instead of raising.
(d) Remove the dead `COMPLETED/FAILED/WAITING` targets from `_ALLOWED_TRANSITIONS[RUNNING]`
or document them as reserved.

**Tests:** API test — `start` on IDLE is rejected and chat still works; manager test —
stop during interaction leaves STOPPED and chat raises cleanly; pause cannot strand an
interaction.

**Dependencies:** none. Do first.

### C2 — UI shows "running" forever after every chat · CONFIRMED

**Evidence:** returning to IDLE publishes only `agent.status_changed`
(`AgentManager.finish_interaction` passes `event_type=None`). `use-agents.ts:11-21`
`AGENT_EVENT_TYPES` does not include `agent.status_changed`, so the card received
`agent.started` (→ refetch → running) and never refetches again.

**Impact:** every Agent card shows *Running* + *Pause* after its first chat. Combined with
C1, a user who clicks Pause gets a 409 (or, on timing, strands the Agent).

**Fix:** handle `agent.status_changed` in `use-agents.ts` (payload already carries `status`;
upsert locally, no refetch needed) and also upsert `response.agent` from the chat response
(authoritative REST state). No new event type is needed.

**Tests:** frontend has no test runner (see §5); verify manually + add a hook test once a
runner exists.

### C3 — Website-created Agents cannot chat · CONFIRMED (known issue)

**Evidence:** UI-style create (`name/description/type`) → initialize → chat →
`503 "Agent has no configured LLM model."` The frontend `Agent`/`CreateAgentInput`
types do not even contain `llm_model` / `allowed_tools`.

Backend also accepts invalid configuration silently: creating with
`provider:"nope"` and `allowed_tools:["rm_rf","calculator"]` → **201**.

**Fix:** core of v0.10E-B (§7).

### B0 — Environment: no API keys in `.env` · CONFIRMED (not a code bug)

Blocks the live E2E test. User action: paste keys into `.env` locally (never into chat).

## 3. High-priority architectural risks

### H1 — Failed turns poison the session · CONFIRMED
`chat_with_summary` appends the user message *before* calling the LLM and never rolls it
back. Live: after 4 failed chats the session held **4 orphan user messages**, all of which
will be resent as context on the next successful turn. A failure *after* tool calls also
leaves `assistant(tool_calls) + tool` messages with no final answer.
**Fix:** build the turn in a local list and commit it to the session atomically on success;
on failure commit nothing (tool side effects are already observable via Tool Runtime history).
**Test:** LLM raises → session unchanged; LLM raises on continuation → session unchanged.

### H2 — The Agent's description never reaches the LLM · CONFIRMED (code)
`AgentContextAssembler.assemble` does `del agent, context` and returns only the user
message. There is no system prompt, so every Agent behaves identically apart from its tool
allowlist; "description" is purely cosmetic. This matters for v0.10E-B because the Create
flow should ask "what should this Agent do?" and have that actually take effect.
**Fix:** add an `instructions: str` field (separate from the human-facing description —
see §8) and emit it as a `SYSTEM` message. Both providers already map SYSTEM correctly
(`system_instruction` for Gemini, `system` role for OpenAI).

### H3 — OpenAI reports `configured: true` without a key · CONFIRMED
`openai_provider.py:31` hardcodes `metadata={"configured": True}`; Gemini computes it.
The model picker in v0.10E-B needs this flag to be truthful. One-line fix + test.

### H4 — SDK timeouts are reported as generic 502s · PLAUSIBLE
Both adapters catch only `asyncio.TimeoutError`. google-genai (httpx) and openai
(`APITimeoutError`) raise their own types, which fall into `except Exception` →
`LLMProviderError` → 502 instead of `LLMTimeoutError` → 504. The handoff's earlier
"504/499" observations are consistent with this path being imprecise.
**Fix:** map `httpx.TimeoutException` / `openai.APITimeoutError` explicitly; test with fake
clients that raise those types.

### H5 — Legacy duplicate subsystems are still wired into live endpoints · CONFIRMED
Two generations of several subsystems coexist:

| Live (used) | Legacy scaffold (registered in DI) |
|---|---|
| `tool_runtime.ToolRuntimeManager` | `tool_manager.ToolManager` (empty) |
| `workflow_runtime.WorkflowManager` | `workflow_engine.WorkflowEngine` (empty; publishes untyped string events) |
| `MemoryManager.create/list/...` + `InMemoryProvider` | `MemoryManager.register/store/retrieve` + `InMemoryMemory` |

`/api/system/tools|workflows|memory` read the **legacy** objects, so they always return
`[]`. Visible effect: the Dashboard shows **"Registered Tools: 0"** while 5 tools exist
(verified in browser). `AgentInteractionService(tool_manager=...)` actually takes a
`ToolRuntimeManager`, which adds naming confusion.
**Fix now (small):** point the three system endpoints at the live runtimes.
**Fix later (separate cleanup milestone):** delete the legacy modules + their tests after
confirming no references.

### H6 — Unbounded session context · CONFIRMED (code)
The full session (including tool messages) is resent each turn with no cap. Long chats will
grow cost linearly and eventually hit the context window. **Recommend** a simple
"last N turns" window (turn-aligned, never splitting a tool-call/tool-result pair) in the
sessions milestone; not required for v0.10E-B.

### H7 — EventBus delivers synchronously, including WebSocket broadcast · PLAUSIBLE
`EventBus.publish` awaits every subscriber inline; `RealtimeGateway.broadcast_event` awaits
`send_json` on every client. A slow/backpressured client therefore delays every publisher —
including the Agent tool loop. Handler exceptions are swallowed with no log.
**Recommend:** log swallowed handler errors now (cheap); add a per-send timeout later.
Do not introduce a queue/broker yet.

### H8 — Frontend realtime is a single-slot `latestEvent` · PLAUSIBLE
`useRealtime` stores only the latest event in state; consumers react via
`useEffect([latestEvent])`. Bursts (one chat produces ~8 events within milliseconds) can be
coalesced by React, so intermediate events may never reach `use-agents` etc. REST refetch on
the last event usually hides this, but it is fragile.
**Recommend:** for v0.10E-B, rely on REST responses for the actor's own actions and keep
events for *other* changes; later, expose a subscriber callback API from `RealtimeService`
instead of state.

### Medium / Low

- **M1 Chat isn't an Execution.** Interactions have their own `interaction_id` and never create
  an `Execution`; `ExecutionExecutor` is still a 2 s placeholder (unless metadata names a tool).
  The Agents page exposes an "Execute" button that runs this dummy job. Acceptable for now,
  but the UI should not present it as a primary action. Long-term decision deferred (§6).
- **M2 Workflow edge cases.** Two concurrently failing tasks each publish `workflow.failed`;
  `_block_dependents` marks *running* siblings BLOCKED, then their completion overwrites them;
  `_workers` entries are never removed. Low impact, add tests when Workflows are touched.
- **M3 `/api/tools/execute`** chooses 404 vs 422 by substring-matching `"was not found"`.
- **M4 No auth on any endpoint.** Fine for localhost; must be addressed before any deployment.
  Dev CORS allows only `http://localhost:3000`, while frontend services default to
  `http://127.0.0.1:8000` — opening the UI at `127.0.0.1:3000` breaks every REST call.
- **M5 Chat error UX discards backend detail.** `use-agent-conversation.ts` replaces every
  non-409 error with "Unable to generate a response", hiding actionable messages like
  "Gemini is not configured".

## 7. v0.10E-B — Agent Creation, Conversation UX, Product Experience

### Goal
A normal user opens Genesis, creates an Agent in one dialog, and asks it
"Calculate 25 × 4" — no Swagger, no lifecycle buttons, no JSON.

### Phase 0 — Backend correctness (half a day)
- C1 lifecycle ownership fix + tolerant `finish_interaction`.
- H1 atomic session turns.
- H3 OpenAI `configured` flag.
- H5 system endpoints read live runtimes.
- Tests for each. *No frontend changes in this phase.*

### Phase 1 — Agent configuration API (half a day)
- `AgentCreateRequest` validation: provider must be registered (422); every `allowed_tools`
  entry must exist in Tool Runtime (422). Unconfigured-but-registered provider is **allowed**
  (Agent can be fixed later by adding a key) and surfaced via `configured`.
- New `instructions` field on Agent (domain + schema + response), default `""`;
  `AgentContextAssembler` emits it as a SYSTEM message when non-empty (H2).
- `PATCH /api/agents/{id}/config` for `llm_model`, `allowed_tools`, `instructions`,
  allowed only while IDLE/CREATED — so existing model-less Agents can be repaired from the UI.
- Optional `initialize: bool = false` on create so the UI can create a ready Agent in one call.
- Session response: include safe per-message tool info (`tool_name`, `status`; never raw
  arguments) so the UI can show tool activity per turn after reload.

### Phase 2 — Create Agent dialog (1 day)
- Fields: **Name**, **What should this Agent do?** (instructions), **Model** (select from
  `/api/llm/models`; unconfigured models disabled with "Add GEMINI_API_KEY to .env"),
  **Tools** (checklist from `/api/tools` with descriptions; calculator/echo preselected).
- Advanced (collapsed): description, type, tags.
- Creates *and* initializes; dialog focus trap and focus return; inline validation;
  backend 422 messages shown.

### Phase 3 — Agent workspace (1–1.5 days)
- Layout: Agent list (left) + conversation (right); on mobile, list → conversation drill-in.
- Remove lifecycle buttons; card shows Ready / Working / Needs setup / Stopped (text + icon,
  not color only). Stop + Delete move into an overflow menu with confirmation.
- Messages: tool activity rendered inline per turn as a compact chip ("Used calculator ·
  25*4 → 100"), expandable; rejections explained in plain language.
- Actionable errors (pass through backend `detail` for 503 configuration errors).
- Reconcile `agent.status_changed` + upsert `response.agent` (C2). Auto-scroll; textarea with
  Enter-to-send / Shift+Enter newline.
- Move agent/execution stats + Execute button into an expandable "Details" panel or
  Monitoring.

### Phase 4 — Navigation and Dashboard (0.5–1 day)
- Sidebar: WORKSPACE (Dashboard, Agents, Tools, Memory, Workflows) / SYSTEM (Monitoring);
  remove Core/Plugins/Settings; mobile drawer with focus management.
- Remove dead Topbar buttons or make the theme toggle real; version from `/api/system/health`.
- Dashboard: "Your Agents" (with Chat links), "Start" CTA when none exist, recent work in
  human language; technical counts move to Monitoring.

### Phase 5 — Secondary pages + quality (1 day)
- Tools / Memory / Workflows hierarchy changes from the handoff; Monitoring human-readable
  event descriptions with expandable raw JSON.
- Fix the 10 lint errors.
- Add a minimal frontend test runner (Vitest + Testing Library — the one new dev dependency
  I would justify) covering `use-agents` reconciliation and the conversation view.

`api/routers/agents.py`, `api/schemas/agents.py`, `api/routers/system.py`,

### Regression risks
- Removing `/start|/pause|/resume` breaks any external script using them → prefer 409 first.
- `instructions` changes LLM behaviour for new Agents only (default empty).
- Create-time validation may reject previously accepted payloads (intended).

### Acceptance criteria
1. From a fresh browser: Create Agent (name + instructions + Gemini + calculator) → Agent is
   Ready without any further click.
2. "Calculate 25 × 4" → answer contains 100; a tool chip shows calculator → 100.
3. Three consecutive chats succeed; card returns to Ready after each without reload.
4. Reload page → conversation and per-turn tool chips are still shown.
5. Without a key: model shows as unavailable at creation; chat error tells the user what to set.
6. No control in the UI can put an Agent into an unrecoverable state.
7. Usable at 375 px; keyboard-only create + chat works; dialog traps focus.
8. Backend tests, `compileall`, `next build`, `eslint` (0 errors), `git diff --check` pass.
